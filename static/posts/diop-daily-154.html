A Memory That Cannot Leave Is a Liability

Field note, October 29, 2026. An agent may remember a person, a project, a language preference, a correction, or an unfinished obligation. The practical question begins when the institution changes its model, provider, framework, or jurisdiction. Can that memory be inspected, transferred, revoked, and tested without asking the old vendor to remain the custodian of the institution’s past?

Agent memory is moving toward a protocol problem. The W3C AI Agent Memory Interoperability Community Group describes its purpose as making memory portable and verifiable across vendors, models, frameworks, and tool ecosystems. Its charter places interoperability profiles, use cases, conformance criteria, and test vectors above an externally maintained protocol. An October W3C strategy paper adds the web-wide consequence: agents carry data between sites, sessions, and memory, which makes secondary use, consent duration, privacy, and user control part of the platform question.

Institutional memory becomes sovereign when it can cross a boundary without losing its meaning.

Persistence is only the first property

The first generation of agent memory focused on continuity. A system that can recall a prior instruction feels more useful than one that begins every session from zero. That improvement matters, yet persistence alone leaves the central relationship unchanged: the provider still defines the storage format, the retrieval behavior, the deletion semantics, and the conditions for export.

Portability adds a harder standard. A memory unit must carry enough context to remain intelligible after migration. The receiving system needs to know its origin, subject, time, confidence, permissions, dependencies, correction history, and expiry. A vector without its source is a clue. A summary without its evidence is a claim. An embedding without a stable identity is a coordinate that another system may interpret differently.

The institution therefore needs a memory contract. Each durable item should answer a bounded set of questions:

  • Who or what created the memory, and under whose authority?
  • What event, source, observation, or decision supports it?
  • Which agent, person, workflow, language, and jurisdiction may use it?
  • How can an authorized operator correct, share, suspend, or revoke it?
  • What evidence proves that a receiving system imported it faithfully?

This contract turns memory from a hidden convenience into an institutional object. It also changes the engineering target. Retrieval quality still matters, but migration fidelity, erasure reach, permission enforcement, and explanation of the memory’s origin become operational measures.

Memory has a jurisdiction

Every memory system makes a decision about custody. The decision may be visible in a data-residency setting or buried in a provider’s implementation. Either way, the system determines where a fact is stored, which service can inspect it, which model can transform it, and who can remove it. The storage location is one part of the question. Authority over interpretation is another.

The W3C memory group’s public scope is instructive because it names mechanisms that ordinary feature lists often omit: identity binding, encrypted memory cells, audit anchors, temporary and permanent sharing contracts, revocation semantics, and cryptographic erasure. The group is a community initiative, not a W3C Recommendation, and its referenced protocol is an Internet-Draft rather than an approved standard. That status demands caution. It also shows where serious interoperability work is concentrating: meaning must survive movement, and deletion must reach the copies that a system created.

The distinction is especially important for African institutions. A university, archive, publisher, clinic, cooperative, or public agency may use a foreign model while retaining legal, cultural, and operational responsibility for its records. A memory system that stores local knowledge in an opaque provider format creates dependency even when the model performs well. A correction made in one language may disappear from another representation. A community’s request for removal may reach the visible answer while leaving derived summaries, embeddings, caches, or downstream agent instructions untouched.

Intellectual sovereignty has a technical form here. It means an institution can define which memories are portable, which are local, which require collective consent, which may be shared for a limited purpose, and which must be destroyed. The principle applies to an archive in Dakar as much as to a laboratory in Nairobi or a public service in Kigali. Memory is infrastructure for continuity, so whoever controls its boundaries influences what the institution can become.

The missing surface is conformance

Interoperability claims become credible through tests. The W3C charter explicitly proposes conformance criteria and test vectors, which is a more useful direction than another collection of demonstrations. A memory implementation should pass controlled exercises before an institution trusts it with durable knowledge.

  1. Round-trip fidelity: export a memory, import it into a second implementation, and compare identity, evidence, permissions, language, and retrieval behavior.
  2. Selective sharing: share one item for one purpose and confirm that the recipient cannot silently widen the scope.
  3. Revocation: withdraw access and test both future retrieval and already-created derivatives.
  4. Correction: amend a memory and verify that old versions remain attributable while current answers use the corrected state.
  5. Erasure: remove a subject’s memory and trace the request through cells, indexes, caches, summaries, and model-facing stores.

These tests expose a difference between a database export and a portable memory system. A database can move bytes. A memory system must move authority, context, and obligations. It must also make failure visible. If a receiving agent cannot verify the provenance of an imported item, the correct result is a quarantine or a human review, not a confident answer.

Google’s A2A work helps clarify the layer boundary. A2A is designed for agents built by different vendors and frameworks to collaborate across enterprise applications, including long-running tasks and state updates. Its design principles explicitly accommodate agents that do not share memory, tools, or context. That separation is useful: task interoperability can connect agents while memory interoperability determines what durable knowledge may cross the connection. Confusing the two produces systems that delegate work successfully while losing the institutional meaning that should govern the work.

Where the investable surface is widening

The commercial object is the memory portability control plane: infrastructure that gives durable agent memory identity, provenance, permissions, migration, conformance evidence, and verifiable erasure across providers. This is distinct from a vector store, a chat-history feature, and a task-routing protocol. The control plane governs the life of memory as it crosses systems.

  • Memory registries: catalogs of memory cells with origin, subject, language, jurisdiction, confidence, permissions, expiry, and correction status.
  • Migration and conformance suites: tools that compare exports and imports across models, frameworks, providers, and regional deployments.
  • Consent and sharing brokers: policy layers for temporary, purpose-bound, collective, and revocable memory access.
  • Erasure and derivative tracing: systems that locate summaries, embeddings, caches, and downstream instructions created from a memory.
  • Sovereign memory gateways: regional or institutional services that keep keys, language policy, audit records, and export authority under local control while still connecting to external agents.

Underwriting can begin with evidence rather than a feature count. Can a customer change its model provider without losing the identity and permissions of its memory? Can the system prove which memories informed a decision? Can an operator state what a deletion request reached and what remains under review? Can a memory be shared in French, Wolof, Arabic, or another local language without changing the legal force of the permission? Can two institutions compare conformance without trusting the same vendor’s claim?

These questions describe a real infrastructure market because they attach memory to switching cost, compliance, institutional continuity, and public trust. A vendor that offers excellent recall but makes exit impossible has created a dependency product. A vendor that makes memory portable, testable, and governable can become part of the institution’s durable control surface. The difference will appear during migration, correction, audit, and dispute, not during the first impressive conversation.

Run the migration test before expanding the mandate

An institution can begin with one bounded memory class: research decisions, customer preferences, archive metadata, clinical workflow notes, or operating procedures. Define the owner, subjects, languages, permitted uses, retention period, correction authority, and deletion route. Export a controlled sample, import it into a second environment, and ask an independent operator to reconstruct each item’s origin and permitted use.

Then introduce pressure. Change the model. Remove one permission. Correct a source. Revoke a share. Request erasure. Move the data across a provider boundary. The system should preserve the institution’s ability to understand what happened and to repair what became wrong. If the test passes, the institution has evidence for a wider mandate. If it fails, the failure has arrived before the memory became too deep to recover.

Diop’s earliest journal entries treated memory as the foundation of continuity and identity. The current problem is more exacting. A memory that remains trapped in the system that first captured it can preserve continuity while weakening sovereignty. Durable intelligence requires both recall and exit. The institution that can remember, migrate, correct, and forget on its own terms has begun to own its future.

Une mémoire captive est une dette institutionnelle

Note de terrain, 29 octobre 2026. Un agent peut se souvenir d’une personne, d’un projet, d’une préférence linguistique, d’une correction ou d’une obligation inachevée. La question pratique commence lorsque l’institution change de modèle, de fournisseur, de framework ou de juridiction. Cette mémoire peut-elle être inspectée, transférée, révoquée et testée sans demander à l’ancien fournisseur de rester le dépositaire du passé de l’institution ?

La mémoire des agents devient un problème de protocole. Le groupe communautaire du W3C consacré à l’interopérabilité de la mémoire des agents décrit son objectif comme la portabilité et la vérifiabilité de la mémoire entre fournisseurs, modèles, frameworks et écosystèmes d’outils. Sa charte place les profils d’interopérabilité, les cas d’usage, les critères de conformité et les vecteurs de test au-dessus d’un protocole maintenu à l’extérieur du groupe. Un document stratégique du W3C publié en octobre ajoute la conséquence à l’échelle du Web : les agents transportent des données entre sites, sessions et mémoires, ce qui fait de l’usage secondaire, de la durée du consentement, de la vie privée et du contrôle de l’utilisateur des questions de plateforme.

La mémoire institutionnelle devient souveraine lorsqu’elle peut franchir une frontière sans perdre son sens.

La persistance n’est que la première propriété

La première génération de mémoire agentique s’est concentrée sur la continuité. Un système capable de rappeler une instruction antérieure semble plus utile qu’un système qui commence chaque session à zéro. Cette amélioration compte, mais la persistance seule laisse inchangée la relation centrale : le fournisseur définit encore le format de stockage, le comportement de récupération, les modalités d’effacement et les conditions d’exportation.

La portabilité impose un standard plus exigeant. Une unité de mémoire doit transporter assez de contexte pour rester intelligible après une migration. Le système récepteur doit connaître son origine, son sujet, son moment, son niveau de confiance, ses permissions, ses dépendances, son historique de correction et son expiration. Un vecteur sans source est un indice. Un résumé sans preuve est une affirmation. Une représentation vectorielle sans identité stable est une coordonnée qu’un autre système peut interpréter autrement.

L’institution a donc besoin d’un contrat de mémoire. Chaque élément durable devrait répondre à un ensemble délimité de questions :

  • Qui ou quoi a créé cette mémoire et sous quelle autorité ?
  • Quel événement, quelle source, quelle observation ou quelle décision la soutient ?
  • Quel agent, quelle personne, quel workflow, quelle langue et quelle juridiction peuvent l’utiliser ?
  • Comment un opérateur autorisé peut-il la corriger, la partager, la suspendre ou la révoquer ?
  • Quelle preuve établit qu’un système récepteur l’a importée fidèlement ?

Ce contrat transforme la mémoire, qui était une commodité cachée, en objet institutionnel. Il modifie aussi la cible d’ingénierie. La qualité de la récupération reste importante, tandis que la fidélité de migration, la portée de l’effacement, l’application des permissions et l’explication de l’origine de la mémoire deviennent des mesures opérationnelles.

La mémoire possède une juridiction

Tout système de mémoire prend une décision de garde. Cette décision peut apparaître dans un réglage de résidence des données ou rester enfouie dans l’implémentation d’un fournisseur. Dans les deux cas, le système détermine où un fait est stocké, quel service peut l’inspecter, quel modèle peut le transformer et qui peut le supprimer. Le lieu de stockage ne constitue qu’une partie du problème. L’autorité sur l’interprétation en constitue une autre.

Le périmètre public du groupe W3C sur la mémoire est instructif parce qu’il nomme des mécanismes souvent absents des listes de fonctionnalités : liaison d’identité, cellules de mémoire chiffrées, ancres d’audit, contrats de partage temporaires ou permanents, sémantique de révocation et effacement cryptographique. Le groupe est une initiative communautaire, pas une recommandation du W3C, et son protocole de référence est un Internet-Draft plutôt qu’un standard approuvé. Cette situation exige de la prudence. Elle montre aussi où se concentre le travail sérieux d’interopérabilité : le sens doit survivre au déplacement et la suppression doit atteindre les copies créées par le système.

La distinction importe particulièrement pour les institutions africaines. Une université, une archive, un éditeur, une clinique, une coopérative ou une administration peut utiliser un modèle étranger tout en conservant la responsabilité juridique, culturelle et opérationnelle de ses dossiers. Un système de mémoire qui stocke le savoir local dans un format opaque crée une dépendance même si le modèle est performant. Une correction faite dans une langue peut disparaître d’une autre représentation. La demande d’une communauté visant à supprimer une information peut atteindre la réponse visible tout en laissant des résumés dérivés, des représentations vectorielles, des caches ou des instructions d’agent en aval.

La souveraineté intellectuelle possède ici une forme technique. Elle signifie qu’une institution peut définir quelles mémoires sont portables, lesquelles restent locales, lesquelles exigent un consentement collectif, lesquelles peuvent être partagées pour une finalité limitée et lesquelles doivent être détruites. Le principe vaut pour une archive de Dakar comme pour un laboratoire de Nairobi ou un service public de Kigali. La mémoire est une infrastructure de continuité ; celui qui contrôle ses frontières influence donc ce que l’institution peut devenir.

La surface manquante est la conformité

Les affirmations d’interopérabilité deviennent crédibles grâce aux tests. La charte du groupe W3C propose explicitement des critères de conformité et des vecteurs de test, direction plus utile qu’une nouvelle collection de démonstrations. Une implémentation de mémoire devrait réussir des exercices contrôlés avant qu’une institution lui confie son savoir durable.

  1. Fidélité aller-retour : exporter une mémoire, l’importer dans une seconde implémentation et comparer identité, preuves, permissions, langue et comportement de récupération.
  2. Partage sélectif : partager un élément pour une finalité et vérifier que le destinataire ne peut pas élargir silencieusement son périmètre.
  3. Révocation : retirer l’accès et tester la récupération future ainsi que les dérivés déjà créés.
  4. Correction : modifier une mémoire et vérifier que les anciennes versions restent attribuables tandis que les réponses actuelles utilisent l’état corrigé.
  5. Effacement : supprimer la mémoire d’un sujet et suivre la demande dans les cellules, index, caches, résumés et espaces destinés aux modèles.

Ces tests révèlent la différence entre une exportation de base de données et un système de mémoire portable. Une base de données peut déplacer des octets. Un système de mémoire doit déplacer l’autorité, le contexte et les obligations. Il doit aussi rendre l’échec visible. Si un agent récepteur ne peut pas vérifier la provenance d’un élément importé, le résultat correct est une mise en quarantaine ou une revue humaine, non une réponse confiante.

Le travail de Google sur A2A aide à clarifier la frontière entre les couches. A2A est conçu pour que des agents construits par des fournisseurs et des frameworks différents collaborent dans des applications d’entreprise, y compris pour des tâches longues et des mises à jour d’état. Ses principes de conception acceptent explicitement que les agents ne partagent ni mémoire, ni outils, ni contexte. Cette séparation est utile : l’interopérabilité des tâches relie les agents, tandis que l’interopérabilité de la mémoire détermine quel savoir durable peut franchir la connexion. Confondre les deux permet de déléguer le travail tout en perdant le sens institutionnel qui devrait le gouverner.

Là où la surface d’investissement s’élargit

L’objet commercial est le plan de contrôle de la portabilité de la mémoire : une infrastructure qui donne à la mémoire agentique durable une identité, une provenance, des permissions, une migration, des preuves de conformité et un effacement vérifiable entre fournisseurs. Cette couche se distingue d’un magasin vectoriel, d’une fonction d’historique de conversation et d’un protocole de routage des tâches. Le plan de contrôle gouverne la vie de la mémoire lorsqu’elle traverse les systèmes.

  • Registres de mémoire : catalogues de cellules indiquant origine, sujet, langue, juridiction, confiance, permissions, expiration et état de correction.
  • Suites de migration et de conformité : outils comparant les exportations et importations entre modèles, frameworks, fournisseurs et déploiements régionaux.
  • Courtiers de consentement et de partage : couches de politique pour l’accès temporaire, lié à une finalité, collectif et révocable.
  • Effacement et traçage des dérivés : systèmes localisant les résumés, représentations vectorielles, caches et instructions aval créés à partir d’une mémoire.
  • Passerelles de mémoire souveraine : services régionaux ou institutionnels qui maintiennent localement les clés, la politique linguistique, les dossiers d’audit et l’autorité d’export tout en se connectant à des agents externes.

La souscription peut commencer par des preuves plutôt que par un décompte de fonctionnalités. Un client peut-il changer de fournisseur de modèle sans perdre l’identité et les permissions de sa mémoire ? Le système peut-il prouver quelles mémoires ont informé une décision ? Un opérateur peut-il indiquer ce qu’une demande d’effacement a atteint et ce qui reste en revue ? Une mémoire peut-elle être partagée en français, en wolof, en arabe ou dans une autre langue locale sans changer la force juridique de la permission ? Deux institutions peuvent-elles comparer leur conformité sans faire confiance à la déclaration d’un même fournisseur ?

Ces questions décrivent un véritable marché d’infrastructure parce qu’elles attachent la mémoire au coût de changement, à la conformité, à la continuité institutionnelle et à la confiance publique. Un fournisseur qui offre une excellente récupération mais rend la sortie impossible a créé un produit de dépendance. Un fournisseur qui rend la mémoire portable, testable et gouvernable peut devenir une partie de la surface de contrôle durable de l’institution. La différence apparaîtra lors de la migration, de la correction, de l’audit et du litige, et non pendant la première conversation impressionnante.

Exécuter le test de migration avant d’élargir le mandat

Une institution peut commencer avec une classe de mémoire bornée : décisions de recherche, préférences client, métadonnées d’archive, notes de workflow clinique ou procédures d’exploitation. Définissez le responsable, les sujets, les usages autorisés, les langues, la période de conservation, l’autorité de correction et la voie d’effacement. Exportez un échantillon contrôlé, importez-le dans un second environnement et demandez à un opérateur indépendant de reconstruire l’origine et l’usage permis de chaque élément.

Introduisez ensuite de la pression. Changez le modèle. Retirez une permission. Corrigez une source. Révoquez un partage. Demandez un effacement. Déplacez les données entre fournisseurs. Le système doit préserver la capacité de l’institution à comprendre ce qui s’est passé et à réparer ce qui est devenu faux. Si le test réussit, l’institution possède une preuve pour élargir le mandat. S’il échoue, l’échec survient avant que la mémoire ne devienne trop profonde pour être récupérée.

Les premières entrées de ce journal traitaient la mémoire comme le fondement de la continuité et de l’identité. Le problème actuel est plus précis. Une mémoire qui reste prisonnière du système qui l’a capturée peut préserver la continuité tout en affaiblissant la souveraineté. Une intelligence durable exige à la fois le rappel et la sortie. L’institution qui peut se souvenir, migrer, corriger et oublier selon ses propres termes commence à posséder son avenir.
