The Harm Used a Valid Syntax

An agent can return a clean answer, close a ticket, and still have done the damage. Google’s September 16 description of Agent Anomaly Detection on the Gemini Enterprise Agent Platform names the pattern in operational language: the session looks benign, the usual metrics-based evaluations pass, and only afterward does a reviewer notice that the agent reached for a tool it should never have touched, or acted on a request that quietly widened its own access. The commercial object is a witness that reads the session beside the live request: traces, tool calls, execution flow, and a finding that can be triaged without slowing the answer.

This is a vendor-published product-direction signal in private preview, not independent evidence of detection quality, coverage, or public adoption. Its value for a laboratory is architectural. Risk in an agent system migrates from the code that was reviewed before deployment to the behavior that appears only while the machine is working. A closed ticket is a completion signal. It is a weak verdict on whether the session stayed inside the institution’s intent.

The ticket can close while the session still needs a witness.

Competence is a poor detector

The more decisions an agent makes at runtime, the more its risk lives in sequences rather than in a single function. A refund agent can issue a syntactically valid payment for the wrong class of goods. A records agent can update a field it was never meant to see. A support agent can follow a user’s wording into a privilege the institution never granted. None of these events need to crash. They can look like work: a refund posted, a record updated, a ticket resolved, a user thanked.

Google’s September 15 post on zero-trust agents states the limit of build-time controls with useful precision. A SQL parser cannot tell a socially engineered refund from a legitimate one if the syntax is valid. A regular expression cannot distinguish a physical accessory from a software license. A single-turn test suite cannot catch a fleet being drained across several turns. Those controls remain necessary. They catch cases that can be specified in advance: unsigned writes, kernel escape, blocked strings, missing signatures. They leave a remainder: proposed actions whose form is legal and whose meaning is wrong.

The missing predicate is intent, judged against the user’s request and the institution’s rules. Google describes an LLM-based policy engine that evaluates each proposed tool call before the call runs, together with log and telemetry analysis that flags unusual behavior across a session. The first check sits on the action. The second reconstructs the story the action belonged to. An institution that owns only the first check will block some bad calls and still miss a session that stayed just inside every local rule while changing its own reach.

Intent has to become a field

Intent is often treated as a psychological guess about the user. In an agent runtime it is a recordable relationship among four objects: the stated request, the permitted tools, the proposed action, and the accumulating session. A refund of 120 dollars for a software license can be valid syntax and still violate a rule that digital products must go to a human manager. The finding is useful only if it preserves the action name, the rationale, the business rule, the user request, and the decision to block, allow, or escalate.

A session witness therefore needs a compact schema that can travel from the live agent to a reviewer, a security owner, and a successor system:

  • Session identity: a durable identifier, start and end time, workflow, principal, language, and the agents that participated.
  • Stated intent: the user’s or institution’s request, including later turns that changed the task.
  • Proposed actions: each tool call, its arguments, the policy that judged it, and whether it ran, blocked, or routed to a person.
  • Observed traces: reasoning traces, OpenTelemetry spans, token and resource use, and any widening of identity or access.
  • Finding: the anomaly class, confidence, mapped risk category, owner, and the evidence a reviewer would need to reopen the session.
  • Disposition: containment, token revocation, human review, disclosure status, and the conditions under which the case may be closed.

Google’s private-preview description maps findings to a focused set of risks from the OWASP Top 10 for Agentic Applications (2026): tool misuse, identity and privilege abuse, cascading failures, and rogue agents, plus operational risks such as resource exhaustion and token-usage escalation. That mapping is a vendor claim about a detector catalog, not a proof that those categories exhaust institutional harm. It does show why a local label such as “weird session” is too weak to underwrite. An insurer, a ministry, a bank, or a hospital needs a finding that can sit beside other incidents, be compared across vendors, and be revisited after the model changes.

The witness sits beside the request

Latency is the reason many institutions skip this layer. If every second look sits on the live path, the agent becomes slower, costlier, and easier to disable under pressure. Google’s description of Agent Anomaly Detection insists on a different placement: analysis runs asynchronously and out of band from the live request path, reading logs and traces the agents already emit. The live answer can still be fast. The institution still receives a finding that the completed session exceeded its intended boundary.

Out-of-band placement changes ownership. Google’s zero-trust series argues that governance should be defined and managed by a platform or security administrator, separate from the agent developer, because the platform enforces it outside the agent code. That separation is an institutional claim as much as an engineering one. The person who ships a refund agent should not be the only person who can see whether the agent refunded a license as if it were a cable. The witness belongs to the institution that bears the consequence.

Identity makes the same point in another vocabulary. On September 15, NIST finalized implementation guidelines in NIST IR 8587 on protecting tokens and assertions from forgery, theft, and misuse. The publication is designed to help organizations avoid exposing tokens to attackers. In an agent session, identity and privilege abuse is often a token event: the machine obtained, reused, forwarded, or widened a credential that should have stayed bounded. A session witness that cannot see token use will miss the moment the agent became someone else.

Handoff multiplies the problem. The Agent2Agent protocol describes an open standard for communication among opaque agentic applications, complementary to MCP’s tool access. Once a task leaves one agent and enters another, the live request path fragments. A clean answer in the second agent can hide a privilege change in the first. The witness has to follow the task: session identity, intent, traces, and findings must survive the border, or the institution will audit only the last speaker.

Who defines an anomaly in African institutions

A detector catalog written for a global enterprise platform will miss harms that are locally obvious. A session that looks like ordinary customer support can still route a payment across the wrong mobile-money rail, disclose a patient’s language to an unauthorized clinic desk, or treat a community elder’s request as a generic user prompt. The syntax of the tool call may be valid. The social meaning is not.

African institutions therefore need the power to write the intent policies and the anomaly classes, not only to consume a vendor’s private preview. A university can forbid an agent from widening access to student records after a help-desk turn. A cooperative can require human review when a refund crosses from goods into licenses, land, or livestock. A public archive can treat any tool call that exports heritage metadata as a finding, even when the call succeeds. A ministry can demand that token-usage escalation in a local-language workflow be visible to a local security owner rather than buried in a foreign console.

Intellectual sovereignty appears here as the right to define what counts as a deviation. An imported model can complete a ticket in Wolof, Arabic, Amharic, or French and still have violated a local rule that the platform never encoded. The witness layer is where those rules become operational: as policy text, as trace fields, as findings, and as exportable evidence. Without that layer, African institutions inherit completion metrics and remain blind to the sessions that looked fine.

Where the investable surface is widening

If agents continue to act inside tickets, capital should examine the infrastructure that can reconstruct a session after the answer has already been given:

  • Out-of-band session auditors: services that read traces, tool calls, and execution flow without adding latency to the live path, then emit findings a security owner can triage.
  • Intent policy engines: systems that judge a proposed tool call against stated user intent and institutional rules before the call runs, and preserve the rationale.
  • Trace schemas that survive handoff: records that carry session identity, intent, token use, and findings across A2A, MCP, translation, and human escalation.
  • Finding registries: stores that map local anomalies to shared taxonomies, retain evidence, assign owners, and remain readable after the model or vendor changes.
  • Remediation loops: products that can pause an agent, revoke a token, route a session to a person, repair a record, and reopen a closed ticket with the original traces attached.

The underwriting question is concrete: can an independent reviewer reconstruct what the agent did after a ticket closed with a successful answer? Useful measures include time from session end to finding, false-quiet rate on sessions that later prove harmful, survival of intent and token fields across handoffs, share of findings mapped to a named risk class, mean time to human review, token-revocation latency, local-language policy coverage, and the percentage of closed tickets for which traces remain complete.

This commercial object differs from nearby layers in the archive. A model-behavior case file records unexpected outputs so the institution can learn. A receipt records what an exchange meant after a boundary was crossed. A permission system decides what a machine may touch. A protocol defines how agents speak. The session witness reconstructs a completed interaction that looked competent. Its unit of value is a finding that arrives in time to matter, without sitting on the user’s critical path.

Begin with one workflow that already closes tickets

An institution can start without waiting for a platform-wide overlay:

  1. Choose one workflow that already lets an agent act: refunds, record updates, scheduling, procurement, or citizen correspondence.
  2. Write the intent rules in the institution’s own language: what the user may ask, which tools may run, which identities may be used, and which actions require a person.
  3. Emit traces for every tool call, token use, and handoff, then store them under a session identifier that outlives the ticket.
  4. Run a second process beside the live path that scores the completed session against those rules and against a small set of named risks.
  5. Give a reviewer the original request, the proposed actions, the traces, the finding, and a way to reopen the ticket or revoke the credential.

A capable agent will keep producing answers that look finished. The institution’s work is to keep a witness on the session after the syntax has already succeeded. Harm that used a valid form still belongs in the record, and the record has to arrive without making the living request wait.

Le mal a utilisé une syntaxe valide

Un agent peut renvoyer une réponse propre, clôturer un ticket et avoir néanmoins causé le dommage. La description donnée le 16 septembre par Google d’Agent Anomaly Detection sur la Gemini Enterprise Agent Platform nomme le schéma dans un langage opérationnel : la session a l’air bénigne, les évaluations habituelles fondées sur des métriques passent, et ce n’est qu’après coup qu’un réviseur remarque que l’agent a saisi un outil qu’il n’aurait jamais dû toucher, ou qu’il a agi sur une demande qui a élargi en silence son propre accès. L’objet commercial est un témoin qui lit la session à côté de la requête en direct : traces, appels d’outils, flux d’exécution et un constat que l’on peut trier sans ralentir la réponse.

Il s’agit d’un signal de direction produit publié par le fournisseur, en prévisualisation privée, et non d’une preuve indépendante de qualité de détection, de couverture ou d’adoption publique. Sa valeur pour un laboratoire est architecturale. Dans un système agentique, le risque migre du code relu avant le déploiement vers le comportement qui n’apparaît que pendant que la machine travaille. Un ticket clôturé est un signal d’achèvement. C’est un verdict faible sur la question de savoir si la session est restée à l’intérieur de l’intention de l’institution.

Le ticket peut se clôturer alors que la session a encore besoin d’un témoin.

La compétence détecte mal

Plus un agent prend de décisions à l’exécution, plus son risque habite des séquences plutôt qu’une seule fonction. Un agent de remboursement peut émettre un paiement syntaxiquement valide pour une mauvaise classe de biens. Un agent de dossiers peut mettre à jour un champ qu’il n’était jamais censé voir. Un agent d’assistance peut suivre la formulation d’un usager jusqu’à un privilège que l’institution n’a jamais accordé. Aucun de ces événements n’a besoin de provoquer une panne. Ils peuvent ressembler à du travail : un remboursement enregistré, un dossier mis à jour, un ticket résolu, un usager remercié.

L’article du 15 septembre de Google sur les agents zero-trust énonce avec une précision utile la limite des contrôles définis à la construction. Un analyseur SQL ne peut pas distinguer un remboursement obtenu par ingénierie sociale d’un remboursement légitime si la syntaxe est valide. Une expression régulière ne peut pas séparer un accessoire physique d’une licence logicielle. Une suite de tests en un seul tour ne peut pas attraper une flotte drainée sur plusieurs tours. Ces contrôles restent nécessaires. Ils saisissent les cas que l’on peut spécifier d’avance : écritures non signées, échappement du noyau, chaînes bloquées, signatures manquantes. Ils laissent un reste : des actions proposées dont la forme est légale et dont le sens est faux.

Le prédicat manquant est l’intention, jugée à l’aune de la demande de l’usager et des règles de l’institution. Google décrit un moteur de politiques fondé sur un modèle de langage qui évalue chaque appel d’outil proposé avant son exécution, ainsi qu’une analyse des journaux et de la télémétrie qui signale un comportement inhabituel sur une session. Le premier contrôle siège sur l’action. Le second reconstitue l’histoire à laquelle l’action appartenait. Une institution qui ne possède que le premier bloquera certains mauvais appels et manquera encore une session restée juste à l’intérieur de chaque règle locale tout en changeant sa propre portée.

L’intention doit devenir un champ

On traite souvent l’intention comme une conjecture psychologique sur l’usager. Dans un runtime agentique, c’est une relation enregistrable entre quatre objets : la demande énoncée, les outils autorisés, l’action proposée et la session qui s’accumule. Un remboursement de 120 dollars pour une licence logicielle peut être une syntaxe valide et violer pourtant une règle qui envoie les produits numériques vers un responsable humain. Le constat n’est utile que s’il conserve le nom de l’action, la justification, la règle métier, la demande de l’usager et la décision de bloquer, d’autoriser ou d’escalader.

Un témoin de session a donc besoin d’un schéma compact capable de voyager de l’agent vivant vers un réviseur, un responsable de la sécurité et un système successeur :

  • Identité de session : un identifiant durable, les heures de début et de fin, le flux de travail, le mandant, la langue et les agents qui ont participé.
  • Intention énoncée : la demande de l’usager ou de l’institution, y compris les tours ultérieurs qui ont modifié la tâche.
  • Actions proposées : chaque appel d’outil, ses arguments, la politique qui l’a jugé, et le fait qu’il ait été exécuté, bloqué ou transmis à une personne.
  • Traces observées : traces de raisonnement, spans OpenTelemetry, usage des jetons et des ressources, et tout élargissement d’identité ou d’accès.
  • Constat : la classe d’anomalie, la confiance, la catégorie de risque associée, le responsable et les preuves dont un réviseur aurait besoin pour rouvrir la session.
  • Issue : confinement, révocation de jeton, revue humaine, statut de divulgation et conditions dans lesquelles le dossier peut être clos.

La description en prévisualisation privée de Google associe les constats à un ensemble ciblé de risques tirés du Top 10 OWASP des applications agentiques (2026) : mauvais usage d’outils, abus d’identité et de privilèges, défaillances en cascade et agents voyous, plus des risques opérationnels tels que l’épuisement des ressources et l’escalade d’usage de jetons. Ce mapping est une affirmation du fournisseur sur un catalogue de détecteurs, non une preuve que ces catégories épuisent le mal institutionnel. Il montre pourquoi une étiquette locale du type « session étrange » est trop faible pour souscrire un risque. Un assureur, un ministère, une banque ou un hôpital a besoin d’un constat qui puisse siéger à côté d’autres incidents, être comparé d’un fournisseur à l’autre et être revisité après un changement de modèle.

Le témoin siège à côté de la requête

La latence est la raison pour laquelle beaucoup d’institutions sautent cette couche. Si chaque second regard siège sur le chemin en direct, l’agent devient plus lent, plus coûteux et plus facile à désactiver sous la pression. La description d’Agent Anomaly Detection insiste sur un autre placement : l’analyse s’exécute de manière asynchrone et hors bande par rapport au chemin de la requête en direct, en lisant les journaux et les traces que les agents émettent déjà. La réponse vivante peut rester rapide. L’institution reçoit néanmoins un constat selon lequel la session achevée a dépassé sa frontière prévue.

Le placement hors bande change la propriété. La série zero-trust de Google soutient que la gouvernance devrait être définie et gérée par un administrateur de plateforme ou de sécurité, distinct du développeur de l’agent, parce que la plateforme l’applique en dehors du code de l’agent. Cette séparation est une thèse institutionnelle autant qu’une thèse d’ingénierie. La personne qui livre un agent de remboursement ne devrait pas être la seule à voir si l’agent a remboursé une licence comme s’il s’agissait d’un câble. Le témoin appartient à l’institution qui porte la conséquence.

L’identité dit la même chose dans un autre vocabulaire. Le 15 septembre, le NIST a finalisé des lignes directrices de mise en œuvre dans NIST IR 8587 sur la protection des jetons et des assertions contre la falsification, le vol et le mauvais usage. La publication vise à aider les organisations à éviter d’exposer des jetons aux attaquants. Dans une session d’agent, l’abus d’identité et de privilèges est souvent un événement de jeton : la machine a obtenu, réutilisé, transmis ou élargi une crédentielle qui aurait dû rester bornée. Un témoin de session qui ne voit pas l’usage des jetons manquera le moment où l’agent est devenu quelqu’un d’autre.

Le transfert multiplie le problème. Le protocole Agent2Agent décrit une norme ouverte de communication entre applications agentiques opaques, complémentaire de l’accès aux outils via MCP. Une fois qu’une tâche quitte un agent et entre dans un autre, le chemin de la requête en direct se fragmente. Une réponse propre dans le second agent peut cacher un changement de privilège dans le premier. Le témoin doit suivre la tâche : l’identité de session, l’intention, les traces et les constats doivent survivre à la frontière, sinon l’institution n’auditera que le dernier locuteur.

Qui définit une anomalie dans les institutions africaines

Un catalogue de détecteurs écrit pour une plateforme d’entreprise mondiale manquera des maux localement évidents. Une session qui ressemble à une assistance clientèle ordinaire peut encore router un paiement sur le mauvais rail d’argent mobile, divulguer la langue d’un patient à un bureau de clinique non autorisé, ou traiter la demande d’un aîné communautaire comme une consigne d’usager générique. La syntaxe de l’appel d’outil peut être valide. Le sens social ne l’est pas.

Les institutions africaines ont donc besoin du pouvoir d’écrire les politiques d’intention et les classes d’anomalie, et non seulement de consommer la prévisualisation privée d’un fournisseur. Une université peut interdire à un agent d’élargir l’accès aux dossiers étudiants après un tour de helpdesk. Une coopérative peut exiger une revue humaine lorsqu’un remboursement passe des biens aux licences, à la terre ou au bétail. Une archive publique peut traiter comme un constat tout appel d’outil qui exporte des métadonnées patrimoniales, même lorsque l’appel réussit. Un ministère peut exiger que l’escalade d’usage de jetons dans un flux en langue locale soit visible pour un responsable de sécurité local plutôt que enfouie dans une console étrangère.

La souveraineté intellectuelle apparaît ici comme le droit de définir ce qui compte comme un écart. Un modèle importé peut achever un ticket en wolof, en arabe, en amharique ou en français et avoir néanmoins violé une règle locale que la plateforme n’a jamais encodée. La couche témoin est le lieu où ces règles deviennent opérationnelles : comme texte de politique, comme champs de trace, comme constats et comme preuves exportables. Sans cette couche, les institutions africaines héritent de métriques d’achèvement et restent aveugles aux sessions qui avaient l’air correctes.

Là où la surface d’investissement s’élargit

Si les agents continuent d’agir à l’intérieur des tickets, le capital devrait examiner l’infrastructure capable de reconstituer une session après que la réponse a déjà été donnée :

  • Auditeurs de session hors bande : services qui lisent traces, appels d’outils et flux d’exécution sans ajouter de latence au chemin en direct, puis émettent des constats qu’un responsable de sécurité peut trier.
  • Moteurs de politiques d’intention : systèmes qui jugent un appel d’outil proposé à l’aune de l’intention énoncée et des règles institutionnelles avant l’exécution, et conservent la justification.
  • Schémas de traces qui survivent au transfert : dossiers qui portent l’identité de session, l’intention, l’usage des jetons et les constats à travers A2A, MCP, la traduction et l’escalade humaine.
  • Registres de constats : stores qui associent les anomalies locales à des taxonomies partagées, conservent les preuves, attribuent des responsables et restent lisibles après un changement de modèle ou de fournisseur.
  • Boucles de réparation : produits capables de suspendre un agent, de révoquer un jeton, de transmettre une session à une personne, de réparer un dossier et de rouvrir un ticket clôturé avec les traces originales jointes.

La question de souscription est concrète : un réviseur indépendant peut-il reconstituer ce que l’agent a fait après qu’un ticket s’est clôturé avec une réponse réussie ? Les mesures utiles comprennent le délai entre la fin de session et le constat, le taux de silence trompeur sur des sessions ensuite avérées nuisibles, la survie des champs d’intention et de jeton lors des transferts, la part des constats associés à une classe de risque nommée, le délai moyen de revue humaine, la latence de révocation de jeton, la couverture des politiques en langues locales et le pourcentage de tickets clôturés dont les traces restent complètes.

Cet objet commercial se distingue des couches voisines de l’archive. Un dossier de comportement de modèle consigne des sorties inattendues pour que l’institution apprenne. Un reçu consigne ce qu’un échange a signifié après le franchissement d’une frontière. Un système de permissions décide ce qu’une machine peut toucher. Un protocole définit la manière dont les agents parlent. Le témoin de session reconstitue une interaction achevée qui avait l’air compétente. Son unité de valeur est un constat qui arrive à temps pour compter, sans siéger sur le chemin critique de l’usager.

Commencer par un flux qui clôture déjà des tickets

Une institution peut commencer sans attendre une superposition à l’échelle de la plateforme :

  1. Choisir un flux qui laisse déjà un agent agir : remboursements, mises à jour de dossiers, planification, achats ou correspondance citoyenne.
  2. Écrire les règles d’intention dans la langue de l’institution : ce que l’usager peut demander, quels outils peuvent s’exécuter, quelles identités peuvent être utilisées et quelles actions exigent une personne.
  3. Émettre des traces pour chaque appel d’outil, usage de jeton et transfert, puis les stocker sous un identifiant de session qui survit au ticket.
  4. Faire tourner un second processus à côté du chemin en direct, qui note la session achevée au regard de ces règles et d’un petit ensemble de risques nommés.
  5. Donner à un réviseur la demande originale, les actions proposées, les traces, le constat et un moyen de rouvrir le ticket ou de révoquer la crédentielle.

Un agent capable continuera de produire des réponses qui ont l’air achevées. Le travail de l’institution est de garder un témoin sur la session après que la syntaxe a déjà réussi. Le mal qui a utilisé une forme valide appartient encore au dossier, et le dossier doit arriver sans faire attendre la requête vivante.
